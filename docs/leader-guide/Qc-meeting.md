# 리더 운영가이드 - QC 회의

## 1. 회의 목적

QC 회의는 신규로 등록된 QC 항목을 검토하여 **처리 여부, 우선순위, 담당자, 티켓 생성 여부를 결정하고 기존 QC 항목의 진행 상태를 추적하는 회의**다.

단순히 QC 결과를 공유하는 데 그치지 않고, 발견된 사항을 실제 개발 업무로 연결하고 미처리 상태로 남는 항목이 없도록 관리하는 것을 목적으로 한다.

## 2. 신규 QC 항목 리뷰

QC 위원이 최근 1주간 신규 등록된 QC 항목을 순차적으로 설명한다.

기본적으로 다음 순서로 확인한다.

1. 신규 등록된 미진행 항목
2. 수정 완료된 항목
3. 기타 확인이 필요한 QC 항목

각 QC 항목에 대해서는 다음 내용을 중심으로 설명한다.

* 발생 현상
* 재현 조건
* 기대 동작
* 현재 상태
* 영향 범위
* 관련 화면 또는 기능
* 수정 여부

QC 위원의 설명이 끝나면 리더가 필요한 질문을 하고 해당 항목의 처리 방식을 결정한다.

---

## 3. 처리 방식 결정

QC 항목은 검토 후 크게 다음 방식 중 하나로 처리한다.

### ① 티켓 생성

별도의 개발 일정과 진행 상태 관리가 필요한 경우 자체 티켓 시스템에 개발 티켓을 생성한다.

티켓 생성 후에는 네이버 프로젝트의 해당 QC 항목에도 담당자를 지정하여 **QC 항목과 개발 티켓 모두에서 담당자를 확인할 수 있도록 한다.**

---

### ② 담당자 지정 후 바로 처리

작업 규모가 작거나 별도 티켓으로 관리할 필요가 없는 사항은 티켓을 생성하지 않고 담당자만 지정하여 처리한다.

QC 내용을 확인하면서 BE 또는 FE 업무인지 즉시 판단한다.

판단이 명확하지 않은 경우에는 **BE와 FE 담당자를 모두 지정하여 먼저 원인 및 담당 영역을 확인하도록 한다.**

담당자는 네이버 프로젝트의 해당 QC 항목에 지정한다.

---

### ③ 보류

개발 공수 대비 개선 가치가 낮거나 현 시점에서 처리 우선순위가 낮다고 판단되는 경우 보류할 수 있다.

보류 시에는 단순히 처리하지 않는 것이 아니라 **보류 사유를 명확하게 기록하고 QC 항목 상태도 보류로 변경한다.**

예:

* 영향도가 낮음
* 재현 가능성이 낮음
* 개발 공수 대비 개선 효과가 작음
* 향후 구조 변경 시 함께 처리 예정

---

### ④ SD팀 전달

특정 고객사만 요구하는 기능 또는 특정 고객 환경에만 적용되는 사항은 제품 공통 기능이 아니라 **고객사 Custom 요건**인지 판단한다.

Custom 요건으로 보는 것이 적절한 경우 제품 개발팀에서 직접 처리하기보다는 SD팀에서 대응하는 방향으로 논의한다.

해당 내용은 QC 담당자가 SD팀에 전달한다.

---

## 4. 유형별 우선순위 판단

모든 QC 항목을 동일하게 처리하지 않는다.

### 치명 / Bug

서비스나 주요 기능에 영향을 미치는 치명적 사항 또는 명확한 Bug는 **금주 처리 대상 여부를 우선 논의한다.**

긴급하게 처리해야 하는 경우 높은 우선순위를 부여하여 개발 일정에 반영한다.

### Improve / 제안

사용성 개선이나 기능 개선 제안은 모든 항목을 개발 티켓으로 만들지 않는다.

다음과 같은 주요 개선사항을 중심으로 티켓화한다.

* 사용성에 미치는 영향이 큰 경우
* 여러 고객에게 공통적으로 적용될 수 있는 경우
* 제품 완성도 측면에서 개선 가치가 높은 경우
* 향후 반복적으로 문제가 될 가능성이 높은 경우

단순 제안이나 개발 가치가 낮은 항목은 담당자 처리 또는 보류로 결정할 수 있다.

---

## 5. 기존 QC 항목 진행사항 확인

신규 QC 항목에 대한 리뷰가 끝나면 기존 QC 항목의 진행 상태를 확인한다.

주요 확인 대상은 다음과 같다.

* 처리 예정이었으나 아직 진행되지 않은 항목
* 담당자는 지정되었지만 진척이 없는 항목
* 개발 완료 후 QC 재검증이 필요한 항목
* 일정 리마인드가 필요한 항목
* 장기간 상태가 변경되지 않은 항목

특히 **티켓을 생성하지 않고 담당자만 지정했던 QC 항목이 누락되기 쉽기 때문에 우선적으로 확인한다.**

담당자 지정만으로 진행 관리가 어렵다고 판단되는 경우에는 기존 QC 항목이라도 개발 티켓을 생성하여 정식으로 진척을 관리한다.

---

## 6. 리더의 역할

QC 회의에서 리더는 개별 Bug의 기술적인 해결방법을 모두 결정하는 역할보다는, **해당 QC 항목을 조직 차원에서 어떻게 처리할 것인지를 결정하는 역할**에 집중한다.

주요 판단 사항은 다음과 같다.

* 실제 개발이 필요한가
* 티켓으로 관리해야 하는가
* BE / FE 중 누가 확인해야 하는가
* 얼마나 긴급한가
* 제품 공통 개선사항인가
* 고객사 Custom 요건인가
* 개발 공수 대비 처리 가치가 있는가
* 보류할 경우 합당한 사유가 있는가

즉 QC 회의의 기본 흐름은 다음과 같다.

**QC 설명 → 영향도 확인 → 처리 여부 판단 → 담당자 지정 → 티켓 여부 결정 → 우선순위 결정 → 기존 항목 진척 확인**

QC 회의의 핵심은 QC 항목을 많이 등록하는 것이 아니라, **발견된 문제를 적절한 개발 업무로 연결하고 담당자와 상태가 불명확한 항목이 방치되지 않도록 지속적으로 추적하는 것**이다.
